This folder holds a **complete proposed root behavior definition and local handler source**, developed from the user's confirmed draft-enabled BDEF, active/draft table names, and business rules. ## Reading the source: rationale for every declaration and operation

| Source statement / group | Why it exists |
|---|---|
| `CLASS lhc_ServiceRequest DEFINITION` | Names the RAP local handler attached to the root behavior pool. |
| `INHERITING FROM cl_abap_behavior_handler` | Inherits RAP handler facilities, including typed messages and transactional callback infrastructure. |
| `PRIVATE SECTION` | The behavior runtime calls the callback methods; they are not public business APIs. |
| `METHODS get_global_authorizations FOR GLOBAL AUTHORIZATION` | Matches root `authorization master ( global )`; the framework needs a concrete authorization decision implementation. |
| `IMPORTING REQUEST requested_authorizations ... RESULT result` | Receives which rights RAP asks for and returns the allowed/denied flags in generated callback types. |
| `METHODS SetDefaults FOR DETERMINE ON MODIFY` | Declares the method called by the BDEF create determination. |
| `IMPORTING keys FOR ServiceRequest~SetDefaults` | Supplies the transactional keys of affected requests. |
| `METHODS ValidateRequest FOR VALIDATE ON SAVE` | Declares the save-phase consistency check (called during draft preparation/activation according to BDEF). |
| `IMPORTING keys FOR ServiceRequest~ValidateRequest` | Supplies keys for instances to validate, not arbitrary database records. |
| `METHODS StartRequest ... FOR ACTION ... RESULT result` | Declares custom RAP action with updated entity result for consumers. |
| `METHODS CloseRequest ... FOR ACTION ... RESULT result` | Declares closing operation, separate from an unrestricted status field edit. |
| `METHOD get_global_authorizations.` | Implements global authorization decision for CRUD and action authorization-by-update. |
| `requested_authorizations-%create = if_abap_behv=>mk-on` | Only populate a response for rights requested by RAP. |
| `result-%create = if_abap_behv=>auth-allowed` | Grants creation **to all callers** in this isolated demonstration; replace with actual roles/permission checks before any real deployment. |
| `result-%update ... auth-allowed` | Grants update and (via BDEF action authorization) start/close in the fictional trial. |
| `result-%delete ... auth-allowed` | Grants delete in the fictional trial. **Unsafe for commercial/production use.** |
| `METHOD SetDefaults.` | Defines creation-time defaults. |
| `READ ENTITIES OF ... IN LOCAL MODE` | Reads the current RAP transactional image from inside its own handler; this differs from direct SQL reads. |
| `ENTITY ServiceRequest` | Selects the entity alias declared by the root BDEF. |
| `FIELDS ( Priority Status )` | Reads only fields used by the determination. |
| `WITH CORRESPONDING #( keys )` | Builds the read key table from generated handler keys, including the transactional key context. |
| `RESULT DATA(lt_requests)` | Receives the current rows for processing. |
| `FAILED DATA(ls_read_failed)` | Records any failed instance reads. Investigate failures before treating the corresponding row as current. |
| `DATA lt_updates TYPE TABLE FOR UPDATE ZZMPR_SERVICEREQUEST01` | Uses RAP-generated update type, retaining %tky and %control structures. |
| `LOOP AT lt_requests ASSIGNING FIELD-SYMBOL(<request>)` | Processes each affected request without copying the table row. |
| `IF Priority/Status IS NOT INITIAL ... CONTINUE` | Leaves requests with explicit values unchanged and avoids unnecessary reupdates. |
| `APPEND INITIAL LINE ... ASSIGNING <update>` | Creates one update payload per row that needs defaulting. |
| `<update>-%tky = <request>-%tky` | Targets the *same transactional/draft instance*, not an arbitrary active UUID. |
| `<update>-Priority = ...default_priority( )` | Centralizes Medium as the fallback priority in the pure rule class. |
| `<update>-%control-Priority = if_abap_behv=>mk-on` | Marks **only** Priority as changed; critical when Status is already supplied by the user. |
| `<update>-Status = ...default_status( )` | Centralizes Open as the new-request state. |
| `<update>-%control-Status = if_abap_behv=>mk-on` | Marks only Status as changed when it is missing. |
| `IF lt_updates IS NOT INITIAL` | Skips a no-op modify, minimizing recursive determinations and framework work. |
| `MODIFY ENTITIES ... IN LOCAL MODE ... UPDATE FROM lt_updates` | Applies default changes through RAP's transactional buffer rather than direct table updates. |
| `FAILED/REPORTED ... ls_modify_*` | Collects internal write failures/messages; production integration should explicitly propagate/handle any unexpected failure. |
| `METHOD ValidateRequest.` | Begins business consistency enforcement. |
| `READ ENTITIES ... FIELDS ( Title Priority Status )` | Reads required properties, including current draft values. |
| `APPEND LINES OF ls_read_failed-servicerequest TO failed-servicerequest` | Prevents silently passing rows that RAP could not read. |
| `DATA(lv_invalid) = abap_false` | Initializes one failure summary per service request. |
| `valid_title( CONV string( <request>-Title ) )` | Uses standalone title policy and converts fixed-length entity field to string. |
| `%msg = new_message_with_text(... severity-error ...)` | Supplies a user-readable RAP error message. Prefer durable message-class IDs and language translations for production. |
| `%element-Title = if_abap_behv=>mk-on` | Identifies the erroneous field for Fiori highlighting. |
| `valid_priority(...)` | Rejects any priority outside L/M/H even if Fiori value help is bypassed. |
| `%element-Priority` | Marks the Priority field as the cause of the error. |
| `valid_status(...)` | Rejects any status outside O/I/C, regardless of UI. |
| `%element-Status` | Highlights the Status field for an invalid value. |
| `APPEND VALUE #( %tky = ... ) TO failed-servicerequest` | Rejects saving one invalid BO instance; RAP performs transactional failure processing. |
| `METHOD StartRequest.` | Implements intentional Open → In Progress transition. |
| `can_start( <request>-Status )` | Uses one shared business policy, tested independently from RAP. |
| `CONTINUE` in rejected branch | Prevents an invalid status transition from reaching the write batch. |
| `Status = 'I'` | New status for a successfully started request. |
| `METHOD CloseRequest.` | Implements intentional In Progress → Closed transition. |
| `can_close( <request>-Status )` | Prevents closing an Open or already Closed request. |
| `Status = 'C'` | New status for a successfully closed request. |
| `READ ENTITIES ... ALL FIELDS ... RESULT DATA(lt_after)` | Fetches updated instances for the action output after an allowed write. |
| `result = VALUE #( FOR request IN lt_after ... %param = request )` | Returns changed BO instances using RAP's action-result structure. |
| `ENDMETHOD` and `ENDCLASS` | Close method and local class implementation, not a second global class. |

Every ABAP line in the implementation is represented by a statement or group above. Structural whitespace, ABAP periods, and comments do not execute.

## Root BDEF: what each addition changes

- `field ( readonly ) Status;`: prevents arbitrary end-user updates to status; actions and LOCAL MODE code handle transitions. **Existing Fiori behavior changes**: Status will not be an editable Create field.
- `field ( mandatory ) Title;`: makes title required in model metadata; `ValidateRequest` enforces actual checks.
- `determination SetDefaults on modify { create; }`: invokes server defaulting during Create.
- `validation ValidateRequest on save { create; update; }`: runs on save of new/changed BO instances.
- `action ( authorization : update ) StartRequest result [1] $self;`: exposes Start action and returns the changed entity, authorized like update.
- `action ( authorization : update ) CloseRequest result [1] $self;`: exposes Close action and returns changed entity.
- `draft determine action Prepare { validation ValidateRequest; }`: runs validation during draft prepare workflow. Confirm behavior in ADT for current release.
- Existing `Activate`, `Discard`, `Edit`, `Resume`, numbering, ETags, field-to-table mappings: preserved from the provided BDEF.

## Important correctness checks / known limitations

1. **Activation not done:** No SAP tenant execution interface is connected to this GitHub edit. There may be release-specific syntax or generated-class conflicts. Fix those using ADT compiler messages, not by assuming repository code is verified.
2. **Draft UI:** Field behavior and draft `Prepare` can interact with Fiori validation. Test Create, Save, Edit, Activate, and Draft Discard.
3. **Global authorization is permissive:** The code intentionally allows all CRUD requests and update-authorized actions. This is only for fictional test data; implement role checks before production or paid code release.
4. **Action result handling:** Examine failures of post-update READ and remove result entries for unsuccessful modifications; current snippet is a minimal teaching implementation.
5. **Internal failures:** Defaulting collects but does not explicitly propagate errors from internal MODIFY; improve diagnostics after integration.
6. **Behavior contract dependencies:** A matching projection behavior definition, projection CDS, service binding and Fiori UI annotations are required for action buttons; the generated definitions are not in GitHub.
7. **Status control:** Setting Status readonly is an intentional business change; test that action updates still work and that the original create scenario no longer requests a mutable Status.
8. **Business transitions:** Restricting generic user updates to Status mitigates bypass, but other behavior implementation code and privileged EML calls must be reviewed.
9. **Type names:** The code uses `TYPE TABLE FOR UPDATE ZZMPR_SERVICEREQUEST01` and alias `ServiceRequest` as expected from the supplied BDEF; if ADT generated another association/method signature, reconcile it.
10. **Product readiness:** Do not claim full end-to-end delivery until BDEF + CDS + tables + metadata + class local types + service are exported, activated and regression-tested together.
